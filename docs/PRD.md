# 「破雾」产品需求文档（PRD）

- **版本**：v0.1
- **状态**：概念验证 / 黑客松 MVP
- **赛道**：知乎黑客松 2026「知识炼金场」
- **暂定名称**：破雾
- **MVP 垂直领域**：计算机专业新生
- **一句话定位**：结合知乎从业者真实经验、专业学习规律和市场需求，为大学生生成可解释、可执行、会动态调整的成长路线。

---

## 1. 产品背景

刚进入大学的学生通常能获得学校培养方案和课程表，却很难理解：

- 所学专业在真实行业中有哪些方向；
- 不同岗位实际做什么、需要什么能力；
- 学校课程、课外自学、项目实践和就业之间有什么关系；
- 如何从大量教材、课程、回答和经验帖中筛选适合自己的内容；
- 遇到困难、目标变化或市场变化时，应该如何调整路线。

以计算机专业为例，新生可能只知道“学好教材”，之后才逐渐意识到大学依赖自主学习，并进一步接触高质量课程、国外教材和实践项目。这类关键认知往往来自知乎上的从业者、学长学姐和专业答主，但相关内容分散在不同问题、回答和评论中，用户需要花费较长时间才能自行拼出完整路径。

现有“AI 学习路线”产品通常只生成静态课程清单，存在以下不足：

1. 缺少真实行业经验和来源依据；
2. 不解释路线为什么这样安排；
3. 不区分长期基础能力与短期热门工具；
4. 不以实践成果验证学习效果；
5. 无法根据用户进度和问题持续调整。

## 2. 产品愿景

让刚进入大学、一头雾水的学生，更早看见学校之外的真实行业，并将分散的信息转化为适合自己的行动路线。

产品不承诺“保证就业”，也不盲目推荐热门方向，而是帮助用户：

- 看清一个行业或岗位的真实情况；
- 理解自己与目标之间的能力差距；
- 知道为什么学、学什么、学到什么程度；
- 通过项目和作品证明自己学会了；
- 在进度、兴趣和目标变化时重新规划。

## 3. 产品原则

### 3.1 来源可追溯

关键行业判断、观点和市场信号应展示来源、时间与适用范围，不把模型生成内容伪装成事实。

### 3.2 经验不等于真理

点赞量、权威等级、评论和作者经历都是质量信号，但不能单独作为真伪判断。产品需要展示共识、争议和反例。

### 3.3 能力导向，而非资料导向

路线以“能解释、能应用、能完成作品”为目标，不以看完多少课程、收藏多少资料为目标。

### 3.4 长期基础与短期市场分离

路线同时维护：

- **稳定能力轨道**：编程、系统基础、问题分析、工程协作等；
- **市场实践轨道**：当前岗位常见工具、框架和业务能力。

市场热点可以调整实践内容，但不应轻易替代长期基础。

### 3.5 近期计划优先

长期路线只提供方向，重点生成未来两周可执行计划，并根据反馈滚动更新。

## 4. 目标用户

### 4.1 MVP 核心用户

计算机相关专业的大一新生，特征包括：

- 对专业和行业了解有限；
- 不清楚未来方向或只了解热门岗位名称；
- 有学习意愿，但缺少资料筛选和路线规划能力；
- 希望大学期间建立真实能力，并为项目、实习或就业做准备。

### 4.2 次级用户

- 大二、大三准备实习但发现能力结构不完整的学生；
- 想跨方向学习 AI、后端、产品等领域的学生；
- 刚毕业、希望补齐岗位能力的职场新人。

### 4.3 暂不覆盖

- 需要权威升学、法律或心理咨询结论的用户；
- 只希望得到课程资源列表、不参与反馈的用户；
- 需要自动投递简历、代做作业或代写项目的用户。

## 5. 核心用户问题

### 场景 A：不知道方向

> 我是计算机大一新生，但不知道以后能做什么。

用户需要先理解不同方向的真实工作、基础要求和低成本体验方式，再决定是否深入。

### 场景 B：已经有目标

> 我想学 AI Agent，希望大二前做出项目。

用户需要得到目标诊断、能力差距、学习路线、近期计划和实践项目。

### 场景 C：学习遇到困难

> 我在看 CSAPP，但完全看不懂，是不是不适合学计算机？

用户需要诊断困难来自前置知识、资料难度、学习方式、时间投入还是目标错配，并据此调整路线。

### 场景 D：面对市场焦虑

> 听说前端没有前途了，我是不是应该转 AI？

用户需要看到从业者观点、市场样本、适用边界和低成本探索建议，而不是被单一热门观点引导。

## 6. 产品范围

### 6.1 MVP 必须完成（P0）

1. 用户建立基础学习档案；
2. 用户输入一个目标或困惑；
3. 系统检索并筛选知乎从业者经验；
4. 用户可粘贴招聘 JD，系统提取岗位能力需求；
5. 系统生成行业认知、能力地图和两周行动计划；
6. 路线关键判断附带来源及推荐理由；
7. 用户可汇报进度、困难和目标变化；
8. 系统诊断原因并以明确操作调整路线；
9. 保存用户路线、节点状态和调整记录；
10. 提供可公网访问、无需复杂配置即可体验的 Web Demo。

### 6.2 应当完成（P1）

1. 支持“尚未确定职业方向”的探索模式；
2. 支持知乎全网搜索提供行业报告和企业公开信息；
3. 展示多个知乎观点的共识与争议；
4. 学习节点支持小测、反思问题和实践成果；
5. 生成路线调整前后的可视化差异；
6. 支持导出学习计划或分享卡片。

### 6.3 可选加分（P2）

1. 知乎 OAuth 登录；
2. 基于用户近期收藏生成学习路线；
3. 使用用户关注内容增强个性化；
4. 多专业路线模板；
5. 更复杂的知识图谱可视化；
6. 多 Agent 观点研究与路线评审。

### 6.4 本期明确不做

1. 未经授权爬取 Boss 直聘等招聘平台；
2. 自动投递简历或联系招聘者；
3. 承诺就业结果或预测个人职业成功率；
4. 自动生成可冒充用户原创的课程作业；
5. 精确规划四年内每天的任务；
6. 用单一点赞量决定内容真伪。

## 7. 核心体验流程

### 7.1 首次进入

用户填写最小档案：

- 年级；
- 专业；
- 当前基础；
- 每周可投入时间；
- 当前目标；
- 目标期限；
- 偏好的学习方式（可选）。

填写时间应控制在 2 分钟内。

### 7.2 目标诊断

Agent 根据用户输入追问最多 3 个关键问题，避免问卷过长。需要明确：

- 用户想探索方向还是完成明确目标；
- 希望达到“了解、能做项目、实习、科研”等哪种程度；
- 当前最重要的时间或能力约束。

### 7.3 证据检索

系统调用知乎搜索，优先获得：

- 从业者真实工作经验；
- 学长学姐学习路径；
- 领域常见误区；
- 不同路线的争议观点；
- 具有实践细节的内容。

如果用户提供招聘 JD，则同时提取岗位职责、稳定能力、工具技能、经验要求和高频术语。

### 7.4 生成路线

系统输出四部分：

1. **行业真实画像**：这个方向实际做什么、不做什么；
2. **能力地图**：长期基础、专业能力和市场实践；
3. **阶段路线**：从当前水平到目标的关键阶段；
4. **未来两周计划**：具体任务、预计时间和验收方式。

### 7.5 学习执行

每个学习节点至少包含：

- 节点名称；
- 学习目的；
- 前置知识；
- 核心问题；
- 推荐来源；
- 行动任务；
- 实践产物；
- 完成标准；
- 预计时间。

### 7.6 进度反馈

用户可以使用自然语言反馈：

- 已经完成；
- 内容太难或太简单；
- 某个概念没懂；
- 时间不够；
- 对新方向产生兴趣；
- 学习或职业目标变化；
- 上传或粘贴实践成果。

### 7.7 动态调整

系统先解释诊断，再执行一个或多个路线操作：

- `insert_prerequisite`：插入前置知识；
- `split_topic`：拆分困难节点；
- `replace_material`：替换不适合的资料；
- `add_viewpoint_branch`：增加观点或探索支线；
- `skip_mastered_topic`：跳过已掌握内容；
- `change_depth`：调整学习深度；
- `reschedule`：重新安排计划；
- `change_goal`：确认后切换目标；
- `add_project`：增加实践任务。

每次调整必须展示：

- 调整原因；
- 调整内容；
- 对长期目标的影响；
- 用户下一步应该做什么。

## 8. 功能需求

### FR-01 用户学习档案

系统应保存用户基础信息、目标、时间预算和当前路线。用户可以随时修改，修改后由系统判断是否需要重排计划。

### FR-02 知乎内容检索

系统应支持按用户目标检索知乎内容，保留：

- 标题；
- 摘要；
- 作者；
- 原文链接；
- 点赞量；
- 评论量；
- 权威等级；
- 排序分；
- 发布时间或编辑时间；
- 精选评论（若接口提供）。

系统应缓存检索结果，避免浪费接口额度。

### FR-03 来源评估

系统应从以下维度评估来源，而不是只给单一总分：

- 与目标的相关性；
- 作者或内容权威信号；
- 社区认可度；
- 内容是否具体且包含实践；
- 时效性；
- 与其他独立来源的一致性；
- 是否存在重要反例；
- 适用人群和场景。

点赞分采用对数或分段归一化，避免超高点赞内容占据全部权重。

### FR-04 观点对照

对于存在争议的关键问题，系统应展示：

- 多数来源的共同结论；
- 主要分歧；
- 每种观点适用的条件；
- 根据当前用户目标给出的选择建议。

### FR-05 JD 解析

用户可以粘贴一条或多条招聘 JD。系统应提取：

- 岗位名称；
- 工作内容；
- 稳定基础能力；
- 专业能力；
- 工具或框架；
- 学历、经验等门槛；
- 可通过项目验证的能力。

结果必须标明这是用户提供的招聘样本，不代表整个市场。

### FR-06 能力地图

系统应将能力分为：

- 长期稳定基础；
- 岗位核心能力；
- 当前市场实践技能；
- 可选探索能力。

能力节点应存在前置关系，但 MVP 不要求构建复杂通用知识图谱。

### FR-07 两周行动计划

计划应符合用户每周可投入时间，包含每周目标、具体任务、实践产物和验收方式。任务总预计时间不得明显超过用户预算。

### FR-08 进度状态

学习节点采用以下状态：

```text
未开始 → 已接触 → 能够解释 → 能够应用 → 稳定掌握
```

状态判断参考：

- 用户自我反馈；
- 简短理解检测；
- 小练习；
- 实践成果。

用户可以手动修正状态。

### FR-09 路线调整

Agent 不应在每次反馈后无理由重写整条路线。调整应尽量局部、可解释，并保存版本差异。

### FR-10 来源展示

用户能够从路线节点查看来源卡片，并打开知乎原文。生成内容不得虚构作者、点赞量、链接或市场数据。

## 9. Agent 设计

### 9.1 Agent 职责

Agent 是“学习与行业导航教练”，负责：

- 澄清目标；
- 组织证据；
- 区分事实、经验、观点和建议；
- 规划路线；
- 诊断困难；
- 调整计划；
- 解释决策。

Agent 不负责代替用户学习或完成应由用户完成的项目。

### 9.2 建议工具

| Tool | 作用 |
|---|---|
| `search_zhihu` | 搜索知乎从业经验、专业讨论和学习建议 |
| `search_global` | 搜索企业官网、行业报告等外部资料 |
| `analyze_job_descriptions` | 解析用户提供的招聘 JD |
| `get_learner_profile` | 获取用户基础、时间和目标 |
| `save_learning_route` | 保存结构化能力地图和计划 |
| `record_learning_progress` | 记录反馈、练习和成果 |
| `adjust_learning_route` | 以结构化操作修改路线 |

### 9.3 Agent 输出约束

1. 关键行业判断附近提供来源；
2. 无来源时明确标记为模型建议；
3. 不将招聘样本频率描述为全市场占比；
4. 不把高赞回答描述成权威事实；
5. 目标不清晰时先追问，不直接生成宏大路线；
6. 长期计划保持简洁，近期计划保持具体；
7. 调整路线前说明原因和影响。

## 10. 数据需求

### 10.1 用户数据

```json
{
  "major": "计算机科学与技术",
  "grade": "大一",
  "currentSkills": ["零基础"],
  "weeklyHours": 10,
  "goal": "了解并入门 AI 应用开发",
  "targetDate": null,
  "preferences": []
}
```

### 10.2 招聘样本

```json
{
  "company": "示例公司",
  "role": "AI 应用开发实习生",
  "city": "北京",
  "publishedAt": "2026-08-01",
  "sourceUrl": "https://example.com/job/1",
  "description": "岗位职责原文",
  "requirements": "岗位要求原文"
}
```

MVP 可使用：

- 用户主动粘贴的 JD；
- 企业官方招聘页面的少量公开样本；
- 人工整理且保留来源和时间的演示样本。

不得依赖未经授权的批量招聘平台爬虫。

### 10.3 黄金测试案例

至少准备 10 条输入及人工认可的核心结果，包括：

1. 大一零基础探索 AI 应用开发；
2. 学过 Python，不知道继续看教材还是做项目；
3. CSAPP 学习困难；
4. 因就业焦虑想从前端转 AI；
5. 每周只有 5 小时，需要压缩路线；
6. 提前完成计划，需要提高难度；
7. 目标从就业切换为科研；
8. 用户提供多个要求不同的 JD；
9. 知乎来源观点冲突；
10. 搜索结果不足或接口限流。

## 11. 页面与交互

### 11.1 首页

核心文案：

> 从一个“我想学……”开始，看见真实行业，走出自己的大学路线。

入口：

- 我还不知道方向；
- 我已经有目标；
- 我有一份招聘 JD 想分析。

### 11.2 目标诊断页

以对话方式收集最少信息，展示当前已理解的用户目标，并允许用户确认。

### 11.3 路线主页

建议布局：

- 顶部：目标、期限、每周时间；
- 主区域：能力路线图；
- 侧栏：未来两周计划；
- 下方：行业经验、市场信号和来源卡片；
- 固定入口：汇报进度 / 遇到问题 / 调整目标。

路线视觉概念：

- **灯塔**：长期目标；
- **主路**：核心能力；
- **岔路**：不同方向和争议观点；
- **补给站**：资料与知乎回答；
- **实践点**：项目和练习；
- **脚印**：学习进度。

### 11.4 调整对比页

展示：

```diff
+ 插入：HTTP 与后端 API
- 暂缓：同时学习多个 Agent 框架
~ 调整：RAG 从第 2 周移动到第 4 周
```

并显示调整理由和下一项行动。

## 12. 非功能需求

### 12.1 性能

- 普通页面首屏目标小于 3 秒；
- Agent 首次可见响应目标小于 5 秒；
- 长任务使用流式输出；
- 相同搜索查询优先命中本地缓存。

### 12.2 可靠性

- 知乎 API 失败时展示明确错误，不伪造来源；
- 限流后停止主动重复调用；
- 无搜索结果时允许用户修改关键词或使用基础路线模板；
- 路线保存失败时不得向用户展示“已保存”。

### 12.3 安全

- `ZHIHU_ACCESS_SECRET` 和模型 API Key 只保存在服务端 Secret；
- 不将密钥写入代码、日志、浏览器或 Git；
- Pi Agent 不开放无关的 Shell 和文件修改工具；
- 用户粘贴的 JD 和学习记录不用于未告知的公开展示。

### 12.4 合规

- 遵守知乎开放平台接口规范和频率限制；
- 不批量爬取或滥用知乎用户数据；
- 不在未授权情况下采集 Boss 直聘等第三方平台；
- 明确区分公开信息、个人经验、市场样本与模型建议。

## 13. 成功指标

### 13.1 黑客松展示指标

- 用户能在 3 分钟内完成一次完整体验；
- 能生成一条有知乎来源的路线；
- 能展示至少一次因用户反馈产生的局部路线调整；
- Demo 无需评委配置开发环境；
- API 失败时仍有清晰降级体验。

### 13.2 产品验证指标

MVP 测试阶段关注：

- 路线生成完成率；
- 用户确认“路线符合当前目标”的比例；
- 用户能够理解路线安排原因的比例；
- 两周计划任务接受率；
- 用户反馈后调整建议采纳率；
- 来源卡片点击率；
- 次周回访率。

不以“生成内容长度”或“调用 Agent 次数”作为核心价值指标。

## 14. MVP 验收标准

### AC-01 创建路线

给定“计算机大一、零基础、每周 10 小时、想入门 AI 应用开发”，系统能够生成：

- 行业真实画像；
- 长期基础与市场实践两类能力；
- 分阶段路线；
- 不超过时间预算的两周计划；
- 至少 3 条可打开的知乎来源。

### AC-02 分析 JD

用户粘贴一条招聘 JD 后，系统能够提取基础能力、专业能力和工具要求，并说明单条 JD 不代表整体市场。

### AC-03 处理观点冲突

当来源对“先学框架还是先学原理”存在分歧时，系统展示双方观点、适用条件及结合用户目标的建议，不把任一方描述为绝对真理。

### AC-04 动态调整

用户反馈“CSAPP 太难且每周只有 5 小时”后，系统能够：

- 诊断可能原因；
- 插入或替换合适节点；
- 压缩近期计划；
- 保留长期目标；
- 显示调整前后差异。

### AC-05 来源可信

所有展示的标题、作者、点赞量和链接来自工具结果；工具失败时系统不生成虚假引用。

### AC-06 状态持久化

刷新页面或重新进入后，用户的学习档案、路线、进度和调整记录仍然存在。

## 15. 技术建议

建议技术栈：

```text
Next.js + TypeScript
Pi SDK（Agent Runtime）
SQLite / Drizzle ORM
知乎开放平台 HTTP API
服务端流式响应
```

公网部署通常使用 Linux，而当前官方 `zhihu-cli` 文档主要支持 macOS 和 Windows，因此：

- 本地开发使用官方 Skill/CLI 验证能力；
- 公网应用通过服务端直接调用知乎 HTTP API；
- Pi SDK 禁用无关内置工具，仅注册业务 Tool。

建议模块：

```text
src/
├── app/                  # 页面和 API
├── agent/                # Pi SDK、Prompt、Tool 定义
├── zhihu/                # 知乎 API 客户端与缓存
├── learning/             # 路线、进度与调整逻辑
├── jobs/                 # JD 解析与市场信号
├── db/                   # 用户、路线、来源和版本
└── schemas/              # 结构化输入输出 Schema
```

## 16. 演示脚本

### 3 分钟 Demo

1. **问题（20 秒）**  
   大学生拥有课程表，却不了解真实行业，也不知道如何将课程变成能力。

2. **输入目标（20 秒）**  
   “计算机大一、零基础，想在大二前做出 AI 应用项目。”

3. **生成路线（60 秒）**  
   展示知乎从业者经验、行业画像、稳定能力、市场实践和两周计划。

4. **动态调整（45 秒）**  
   用户反馈“CSAPP 看不懂，而且每周只有 5 小时”，展示诊断及路线差异。

5. **证据与价值（25 秒）**  
   打开来源卡片，展示共识、争议、点赞和适用范围。

6. **总结（10 秒）**  
   “不是让学生收藏更多资料，而是让真实经验最终变成能力和作品。”

## 17. 风险与应对

| 风险 | 应对 |
|---|---|
| 路线看似完整但不实用 | 使用黄金案例人工评审；近期计划必须包含实践和验收 |
| 高赞内容过时或不适用 | 展示时间、适用范围、反方观点与市场样本 |
| 招聘数据不足 | 支持用户粘贴 JD；使用人工整理且可溯源的少量样本 |
| API 限流 | 查询缓存、请求去重、演示预热与降级样本 |
| Agent 频繁重写计划 | 采用结构化局部调整操作并保存版本差异 |
| 功能范围过大 | MVP 只聚焦计算机新生和一个完整黄金流程 |
| 制造就业焦虑 | 强调探索、长期基础和个体差异，不承诺就业结果 |
| 引用幻觉 | 引用只能来自工具返回，失败时明确提示 |

## 19. 已确认决策

- MVP 聚焦计算机专业新生，不在第一版扩展到其他专业。
- 产品采用“行业真实经验 + 正确学习路线 + 市场需求”的三类证据结构。
- 未获得正式授权前，不通过爬虫批量采集招聘平台数据。
